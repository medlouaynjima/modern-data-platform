Bronze Layer
Raw Landing Zone
Every event is captured as-is and stored permanently. Invalid events are quarantined — like a quality control gate on arrival.
What happens here
Every event is saved forever
Duplicates are detected & removed
Bad data goes to quarantine
Full audit trail preserved
▼
🥈
Silver Layer
Clean & Typed Data
Raw JSON blobs become proper structured tables. Every field has the right type, events are deduplicated, and data is ready to query.
What changes here
JSON → typed table columns
Timestamps normalized to UTC
One table per topic (orders, etc.)
Source lineage columns added
▼

What Does the Same Order Look Like at Each Stage?

Follow one customer order through the entire pipeline

🥉 Bronze: The event arrives exactly as the producer sent it — a raw JSON string inside a Kafka message. We save everything including Kafka metadata. No transformation, no judgment. If the data was wrong when sent, Bronze preserves that too.
📬 Kafka message receivedtopic: orders | offset: 8421
// The raw message from the Kafka broker { "topic": "orders", "partition": 1, "offset": 8421, "kafka_timestamp": "2025-06-12T14:23:01Z", "event_key": "order-10847", "event_payload": "{\"event_id\":\"a1b2c3\",\"order_id\":10847, \"customer_id\":42,\"product_id\":115, \"quantity\":2,\"price\":89.99, \"total_amount\":179.98,\"country\":\"France\", \"channel\":\"web\"}", "ingested_at": "2025-06-12T14:23:02.441Z", "ingest_date": "2025-06-12" }
📦 Stored in Bronze Delta Lakedata/bronze/events/
// Saved exactly as above — no changes made // Quarantine check: ✅ passed (valid JSON + schema OK) // Dedup check: ✅ new offset, accepted // Total bronze rows: 84,219 across all topics
🥈 Silver: The JSON payload is parsed and each field gets the correct data type. The messy string becomes a proper structured table row you can actually query with SQL. Invalid or duplicate events are dropped here.
🔧 After parsing & typingdata/silver/orders/ (partitioned by date)
// JSON string is gone — now proper typed columns { "event_id": "a1b2c3", "order_id": 10847, // BIGINT "customer_id": 42, // BIGINT "product_id": 115, // BIGINT "quantity": 2, // INTEGER "unit_price": 89.99, // DOUBLE "total_amount": 179.98, // DOUBLE "country": "France", "channel": "web", "event_timestamp": 2025-06-12T14:22:58, // TIMESTAMP "event_date": 2025-06-12, // DATE (partition key) "source_topic": "orders", "bronze_ingested_at": 2025-06-12T14:23:02 }
✅ What was gained vs Bronze
// Before Silver: event_payload = "{ a 2kb unreadable JSON string }" // After Silver: order_id = 10847 // can now JOIN, filter total_amount = 179.98 // can now SUM() event_date = 2025-06-12 // fast partition pruning // Written to silver/orders: 12,840 rows // Dropped (duplicates): 38 // Dropped (null event_id): 2
🥇 Gold: Multiple Silver tables are joined together and aggregated into business-ready facts. This is the final answer — no more raw data, just the numbers your business actually needs to make decisions.
📊 fct_daily_sales — France, 2025-06-12data/gold/fct_daily_sales/
// orders + products + payments joined & aggregated // One row = one day × product × country × channel { "order_date": 2025-06-12, "product_name": "Electronics Product 115", "sku": "SKU-00115", "category": "Electronics", "country": "France", "channel": "web", "order_count": 47, "customer_count": 39, "units_sold": 94, "gross_revenue": 8459.06, "gross_margin": 2960.17 }
